### 1.2 值得保留的工程结论

1. **联网模块的统一模式**（招标采集 → 邮件提醒）：独立子模块、**默认关闭且关闭时零请求**、
   失败降级不轰炸、凭据脱敏（只回「是否已配置」，不回明文）。
   A2 **不新增联网点**（只是往已有邮件里多写一段）。
2. **提醒的分级口径**：`逾期(红) / 今天(橙) / 临近(灰)` + 安静时段 + 单条「今天不再提醒」。
   A2 直接复用这套分级与交互，不另立一套。
3. **数据库迁移框架**：`SCHEMA_VERSION` + `MIGRATIONS[i]`（升级到 i+1），
   迁移前自动备份。A2 的 v7 → v8 走同一机制，并且 `tools/test-migration-full.js`
   做的是**全链迁移**（从真实旧库或合成的 v1 老库一路升到最新），新迁移必须进这条链。
4. **列表字段缺失 = 数据被清空**（1.10 踩过的坑）：任何给业务表新增的字段，
   必须同步补进该表的列表 SELECT，否则「从列表页打开 → 保存」会把没查出来的字段写空。
   A2 新增两个项目字段，`pm.js` 的列表查询必须同步——**并在测试里专门覆盖这一条**。

### 1.3 B3 报价自定义列（1.15）—— 设计记录

报价要填的规格项因客户而异（炼化要「介质 + 设计温度 + 泄露等级」，水务要
「阀门标准 + 执行器型号 + 限位开关」），固定列永远差一两项。所以做的不是"再加几列"，
而是**让列可以自己加**。

| 存什么 | 存在哪 | 说明 |
|---|---|---|
| 列定义 | `quotation_fields`（v7 新表） | 名称、类型（text/number/select）、单位、候选值、排序、启用 |
| 每行的值 | `quotation_items.extra` / `quotation_template_items.extra` | JSON，**键 = 列 id** |

三条设计红线（都有对应测试）：

1. **不做动态 ALTER TABLE**：每加一列就迁移一次、列名一改就在库里留下对不上号的列。
   列定义 + JSON 值可以任意增删改，**加列不需要再迁移**。
2. **JSON 键用列 id 而非列名** → **改名不丢值**（「泄露等级」→「泄漏等级」，
   历史单据照常显示）。
3. **类型不做数值强转**：`number` 只决定录入控件与导出对齐，避免把「≤80」「PN16」挡在门外。

行为边界：**删列不删值**（只是不再显示，删列接口返回 `used_in` 影响面；
下次保存该单据时孤儿值才被清理）、**停用不删值**、不存在的列 id 直接丢弃、
空值不落库、超长值截断（200 字）。

上限：60 列 / 列名 20 字 / 单位 10 字 / 值 200 字 / 候选值 60 项。

**将来要扩展时改哪里**：

- 想加"列类型"（如日期、计算公式）→ `quotation-field.js` 的 `KINDS` 白名单 +
  前端 `quotation-fields.js` 的录入控件与 `quotation-drawer.js` 的单元格渲染
- 想把自定义列用于**数据导出/打印**而不只是报价单 → 复用 `exportData()` 的
  `custom_columns` 字段（已按列顺序、带单位返回）
- 想加一个**新的内置列** → 在 `quotation-field.js` 的 `BUILTIN_COLUMNS` 里加一条
  （key/label/scope/kind），再在 `quotation-drawer.js`（与模板页）的 `BUILTIN_UI`
  里给它宽度与控件形态、在 `inputAttrs()` 之外补上值绑定即可；
  顺序数组会自动把新列补进合理位置（老用户的顺序不会被冲掉）
- 想按模板区分列（不同模板显示不同列）→ 现在刻意是**全局一套列**；
  要改成"每模板一套"需给 `quotation_fields` 加 `scope/template_id` 并改 `liveFieldIds()`
  的过滤口径，属于结构性改动（当前不做，因为"报价单与模板共用一套列"是刻意的简化）

### 1.4 B4 报价明细列顺序（1.16）—— 设计记录

**需求**：报价模板的「规格明细」里，**每一列都要能移动位置**（不只是自定义列）。

**做法**：把列顺序抽成**一条全局设置**，而不是逐个实体存：

| 存什么 | 存在哪 |
|---|---|
| 列顺序 | 设置项 `quotation_column_order`（JSON 数组，元素为内置列 key 或 `f:<列id>`） |
| 列定义 | `quotation_fields`（1.3，不变） |

四条设计取舍：

1. **不动表结构**：顺序是"界面偏好"不是业务数据，存设置项即可 ——
   **不需要迁移**，升级后老库直接可用。
2. **全局一套**（用户确认的选择）：报价单明细、报价模板明细、导出单据三处一致。
   若做成"每个模板一套"，报价单是跨模板的，套用后仍然要一套统一顺序，
   反而会出现两套顺序打架。
3. **缺列自动补齐**：顺序数组里没有的列（新加的自定义列、将来新版本才有的内置列）
   自动插回合理位置（优先插在"默认顺序里它前一个已存在列"之后），
   **绝不会因为数组不完整而丢列**；已删除列的 key 在读的时候被过滤掉。
4. **合并列取最前位置**：单据里「规格型号」是 5 个规格字段合成的一列，
   它的位置取这 5 个字段里最靠前的那个；「合计」金额跟着「小计」列走，
   挪列也不会错位。

交互：表头右侧 ◀ ▶（鼠标移上去才显形，已在首尾时置灰）+ 列管理抽屉里的 ↑↓，
两处改的是同一套顺序。

### 1.5 B5 内置列改名 / 删除（1.17）—— 设计记录

**需求**：「报价单明细不固定，所有都可以删改」—— 内置列也要能改名、能不显示。

| 存什么 | 存在哪 |
|---|---|
| 列名覆盖 | 设置项 `quotation_column_labels` = `{ 列key: 自定义名 }` |
| 被删掉的列 | 设置项 `quotation_column_hidden` = `[列key, ...]` |

三条取舍：

1. **删除 = 隐藏，不是真删**。内置列对应明细表里实实在在的字段，删掉只是不再显示，
   已填的值仍留在库里，加回来就能看到（界面明确提示这一点）。
2. **四列不许删**：名称/阀种（认不出报的是什么）、数量、单价（金额 = 数量 × 单价）、
   小计（合计的来源）。它们**可以改名、可以移动**，只是不能删。
   接口拒绝时给出原因，界面标「必需」并置灰删除按钮；
   **服务端还会兜底**：直接往设置项里写这些 key 也不生效（读取时过滤）。
3. **改名要能回退**：每列都带 `default_label`，列管理里清空输入框即恢复默认名；
   改名后报价单、模板、导出单据三处一起变。

**将来扩展**：若要再加"必需列"，只需往 `quotation-field.js` 的 `LOCKED_KEYS`
与 `LOCK_REASON` 里加一条 —— 界面与导出都会自动跟着走（都读同一份元数据）。

### 1.6 删列安全性（1.18）—— 验证记录

**要回答的问题**：删掉任意一列（内置或自定义）之后，别的功能还能不能用？

**做法**：`tools/test-quotation-delete-column-safety.js` 把每一列**逐个删掉**，
每删一列就跑一遍报价单全流程：新建 → 读回 → 覆盖保存 → 复制新版本 →
沉淀模板 → 套用模板 → 导出（真出 xlsx 读回）→ 改状态并回填项目合同额 →
总列表/汇总/状态计数；然后恢复该列。必需列则验证"删不掉 + 拒绝后功能照常"。

再补一轮**跨模块冒烟**：把能删的列全删光后，确认首页、客户、项目、待办、日志、
回收站、备份、状态字典都照常，并在"全删"状态下再跑一遍全流程。

**结论**：不存在"删了某一列就坏掉"的情况。数据侧的根据是：
明细的列值都落在 `extra`（JSON，按键存储）里，内置列的值落在各自字段上，
删列只改"显示哪些列"（设置项），**不动任何数据与算法** ——
所以金额计算、模板、版本、导出、统计都不受影响。

### 1.7 B8 公众号采集实测问题修复（1.20）—— 设计记录

**要回答的问题**：使用者拿真实公众号文章试过之后报了两件事 ——
「抓取的公众号总是不符合条件」「内容超过 3M」。为什么自测没发现？

**根因（两条都属于"用自测数据想当然"）**：

| 现象 | 根因 | 教训 |
|---|---|---|
| 真项目文章被判「非新疆本地项目」 | 文章路径**复用了邮件的地域规则**（正文出现外省地名即排除）。邮件里这是对的（一封信通常只写一个地方），但公众号正文里招标代理、设计院、监督单位常年在外省 —— 规则把真项目挡在门外 | 同一条规则换个场景就可能变成错的：**判定要跟数据形态绑定**，不能因为"已经有一个现成的"就直接复用 |
| 图文混排文章抓不下来 | `MAX_BYTES` 按"纯文字公告"估成 3MB；公众号文章带排版与图片说明，5MB 很常见 | 上限要按**最坏的真实输入**定，而不是按理想输入定 |

**改法**（细节见 `CHANGELOG.md` 1.20）：

1. 文章专用地域判定 `extract.judgeXinjiangArticle()`：命中地州 → 30 分；
   **只提到「新疆」也收**（8 分 + 摘要注明"未出现具体地州，请自行确认"）；完全没提新疆 → 拒。
   **邮件路径的 `isXinjiang()` 一行不动** —— 两条路径从此各用各的规则。
2. `wechat.MAX_BYTES` 3MB → **20MB**，报错文案带上具体上限，并加常量断言防回退。
3. 补**人工出口**：结果表逐条「仍收下」+ 底部「把未命中的也收下」→
   内容照常进**待审核**，`notice_type` 记「人工收下」，摘要写明原未命中原因；审计日志照记。
4. 补**诊断工具** `tools/why-rejected.js`：把"抓了几字节 / 地域判定 / 命中词 / 最终原因"摊开，
   下次不用靠猜。

**工程结论**：规则型降噪必须配一个"人已经看过、确认要留"的出口 ——
任何自动口径都会有漏网的真商机，**不能让人被自己的过滤器挡住**。

## 2. A2 · 合同 / 质保期到期预警（下一版第一件事）

### 2.1 现状与痛点（已核对代码）

| 事实 | 位置 | 意义 |
|---|---|---|
| 项目有 `signed_at` / `bid_date` / `start_date` / `end_date` / `delivery_date` | `projects` 表 | 合同期与交付期**已有数据**，可直接用 |
| 项目**没有**验收日期、**没有**质保月数 | `projects` 表（已确认无这两列） | 需迁移新增 |
| 客户有 `warranty_months`（质保月数）与 `warranty_ratio`（质保金比例） | `customers` 表 | 只能当「该客户的常规约定」，用作新建项目时的默认值；质保期本质是**项目级**的 |
| 已有回款计划查询（逾期 / 近期）与核销关联 | `pm.js` 的 `paymentOverview()`、`payments.plan_id` | 将来做「质保金应收」可直接复用，但**计划本身没有款项性质字段** |
| 已有提醒服务与铃铛面板 | `services/reminders.js`、`web/js/reminders.js` | A2 是**扩展现有模块**，不是新建一套 |

**痛点**：项目有签约日、交付期、结束日，但**没有任何「快到期」提示**。

- 质保期到了没跟进（质保金该收了、续单机会来了）；
- 合同交付期临近但货还没发完；
- 已交付但忘了补验收日期 → 质保期永远算不准。

这些现在全靠记忆，而漏掉的都是钱。

### 2.2 方案

#### 2.2.1 质保期起算点：**验收日**（沿用已确认结论）

```
质保期到期日 = accepted_at（验收日期） + warranty_months（质保月数）

accepted_at 为空时（尚未验收）：
  → 退化为「delivery_date（交付期） + warranty_months」作为**预估**，
    界面上明确标注「按计划交付日预估，验收后自动更正」
```

**月份加法采用「日号截断」而不是溢出**：1 月 31 日 + 1 个月 = 2 月 28/29 日（不是 3 月 2/3 日）。
理由：质保期是**商务约定**，用户心里的「12 个月」就是「明年同一天」，
月末溢出到下一月会让人对不上账。实现上用 JS 计算并截断到目标月最后一天，
**测试必须覆盖 1 月 31 日、闰年 2 月 29 日、12 月 31 日 +1 个月**。

> SQLite 的 `date(x,'+1 month')` 对 1 月 31 日会归到 3 月 3 日，**不要**直接用它算质保期。

#### 2.2.2 四类预警与判定

| 类型 | 判定条件 | 提前量 | 级别 |
|---|---|---|---|
| **质保期到期** | `质保到期日` ≤ 今天 + N 天（N = `warranty_remind_days`，默认 30） | 30 天 | 已过期=红；≤7 天=橙；其余=灰 |
| **待验收提醒** | 已过 `delivery_date` 且 `accepted_at` 为空 | — | 橙（推动补录验收日期，否则质保期算不准） |
| **合同交付期** | `delivery_date` ≤ 今天 + N 天（N = `contract_remind_days`，默认 14），且项目未完成 | 14 天 | 逾期=红 |
| **合同结束日** | `end_date` ≤ 今天 + N 天，且项目未完成 | 14 天 | 逾期=红 |

**与跟进提醒相反的一点**：质保期提醒**恰恰发生在项目做完之后**，
所以 A2 的查询**不过滤终态阶段**（`deleted_at IS NULL` 仍然要过滤）。

**同一项目多条命中只出一条**：取最紧急的那条作为列表项，其余在项目详情里列全，
避免一个项目在面板里刷屏。

#### 2.2.3 界面

1. **顶栏铃铛面板**新增「即将到期（N）」板块，排在待跟进板块下方，样式复用现有分组；
2. 每条显示：项目名 / 客户简称 / 「质保到期还剩 X 天」/ 到期日；
3. 点击直达项目详情；支持单条「今天不再提醒」（复用现有 snooze 机制，key 换成 `project_id`）；
4. **项目详情**新增「质保到期日 + 剩余天数」小条，并解释预估口径；
5. **项目表单**新增两个字段：验收日期（日期选择）、质保月数（数字，默认取该客户的 `warranty_months`）。

### 2.4 难点与风险

| 风险 | 说明 | 应对 |
|---|---|---|
| 月末 / 闰年 | 见 §2.2.1 | 自己实现「日号截断」并写边界测试 |
| 验收日期缺失（存量项目必然为空） | 质保期算不出来 | 退化用交付期预估 + 界面标注 + 「待验收提醒」推动补录 |
| **列表字段缺失导致清空** | 1.10 已踩过 | 新字段进 `pm.js` 列表 SELECT，并**单独写一条断言**覆盖「从列表页编辑后字段仍在」 |
| 项目阶段终态 | 与跟进提醒的口径相反 | 明确：A2 **不过滤**终态阶段；测试覆盖「已完成项目的质保期仍然提醒」 |
| 邮件由「有空才发」变「两块都空才不发」 | 会影响既有邮件测试 | 更新 `tools/test-notify-email.js` 的判定，并新增「只有到期项时也要发」的用例 |
| 日期脏值 | 早期录入可能有空值 / 格式不一 | 统一走 `date()` 比较；空值跳过不参与预警 |
| 语义重叠 | 「合同结束日」与「交付期」可能同一天 | 同一项目同一天只出一条，取更紧急的类型 |

**难度：低**（一个迁移 + 一组查询 + 一处面板扩展）
**工作量：0.5 ~ 1 天**（含测试与全量回归）

### 2.5 验收标准（A2 新增 3 项，与既有 31 + 8 项并行有效）

| # | 验收项 | 判定标准 |
|---|---|---|
| **R5** | 到期判定正确性 | 质保到期日按**验收日 + 月数（日号截断）**算出；`accepted_at` 为空时按交付期预估并在界面标注「预估」；月末、闰年 2 月、12 月 31 日边界均有断言；交付期与结束日按各自提前量命中 |

## 5. 风险与回退

- **迁移可回退**：v7 只是给 `projects` 加两列（都有默认值），不动既有数据；
  迁移框架会自动先备份，恢复走「设置 → 备份与恢复」。即使不恢复，多出的两列也不影响旧版本读取。
- **不影响既有功能**：A2 只新增查询、面板板块与两个表单字段，不改变任何既有字段语义；
  `/api/reminders/due` 的返回结构保持不变。
- **离线承诺不变**：A2 是纯本地计算，**不新增任何联网点**；邮件只是往已有那封里多写一段。
- **提醒不吵人**：沿用安静时段 + 单条「今天不再提醒」；同一项目只出一条，避免刷屏。
